# Code Quality

Code quality - это качество кода с точки зрения корректности, читаемости, поддерживаемости, тестируемости и безопасности изменений. Хороший код - это не просто "красивый" код. Он помогает команде понимать, менять и развивать систему без лишнего риска.

Эти идеи также полезны во время [Code Review](code-review.md), где проверяют не только то, работает ли код, но и то, можно ли его безопасно поддерживать дальше.

## Что такое code quality?

Code quality описывает, насколько хорошо код поддерживает свою задачу со временем. Качественный код понятен, предсказуем, покрыт осмысленными тестами и согласован с архитектурой проекта.

Качество зависит от контекста. Маленький скрипт, одноразовая миграция и долгоживущая Android feature не требуют одинаковой структуры. Цель - выбрать самый простой дизайн, который сохраняет текущее поведение понятным, а будущие изменения безопасными.

**Коротко:** code quality - это способность уверенно менять код без постоянных новых багов и замедления будущей работы.

## Readability

Readability означает, что намерение кода понятно. Читатель должен понимать, что делает код, зачем он существует и где находится владелец состояния, без восстановления всей картины из низкоуровневых деталей.

Важные части readability:

- понятные имена классов, функций, переменных и состояния;
- небольшие функции с одной основной ответственностью;
- предсказуемый control flow;
- минимум неожиданных side effects;
- явный владелец mutable state;
- организация кода вокруг meaningful domain или feature concepts.

Readability не означает многословность. Она означает, что важные решения видны, а шум не скрывает поведение.

**Практический совет:** если комментарий должен объяснять, что делает каждая строка, коду, скорее всего, нужны лучшие имена, меньшие функции или более ясная структура.

## Maintainability

Maintainability означает, что будущие изменения можно делать без поломки несвязанного поведения. Поддерживаемый код имеет понятные границы, ограниченную связанность, полезные тесты и явные контракты между слоями.

В Android maintainability часто зависит от того, насколько хорошо разделены UI, state management, domain logic и data access. Изменение API mapping не должно требовать переписывания UI. Изменение UI state не должно протекать во внутренности repository.

Поддерживаемый код также не прячет важное поведение в global state, base classes, magic callbacks или неявных lifecycle assumptions.

**Главная мысль:** maintainability - это не только сегодняшняя реализация. Это снижение стоимости и риска завтрашнего изменения.

## Technical debt

Technical debt - это trade-off или накопленная сложность, которая делает будущую работу медленнее или рискованнее. Он появляется из-за быстрых решений, старых требований, отсутствующих тестов, временных workaround, устаревших dependencies или дизайна, который больше не подходит продукту.

Не каждый debt плохой. Иногда небольшой debt - разумное product decision, особенно если scope понятен и команда планирует к нему вернуться. Риск начинается, когда debt невидим, не описан или расползается по critical paths.

Типичные признаки unmanaged debt:

- изменения занимают намного больше времени, чем ожидалось;
- маленькие фиксы ломают несвязанное поведение;
- тестов нет или их сложно писать;
- важная логика дублируется;
- непонятно, какой слой владеет решением;
- "временный" workaround становится частью архитектуры.

**Важно:** technical debt нужно называть и управлять им. Игнорируемый debt превращается в налог на каждую будущую feature.

## YAGNI

YAGNI означает "You Aren't Gonna Need It". Не добавляй функциональность, абстракции или extension points до того, как для них появилась реальная потребность.

Преждевременная абстракция часто делает код сложнее для чтения и изменения. Generic interface, plugin system или strategy layer могут быть полезны при реальных вариациях, но вредны, если есть только одна implementation и нет конкретного второго use case.

YAGNI не означает отказ от дизайна. Он означает проектирование под известные требования и сохранение кода таким, чтобы его было легко расширить, когда появится реальная потребность.

**Типичная ошибка:** абстракция "на всякий случай" может создать больше maintenance cost, чем будущее изменение, которое она должна была упростить.

## Code smells

Code smells - это признаки того, что в коде могут быть проблемы с дизайном, читаемостью или поддерживаемостью. Это не всегда баги, и они не всегда требуют немедленного refactoring.

Частые примеры:

- long method;
- large class / god object;
- duplicated code;
- feature envy;
- primitive obsession;
- shotgun surgery;
- deep nesting;
- too many boolean flags;
- hidden side effects;
- unnecessary abstraction.

Smell - это сигнал посмотреть на контекст. Иногда правильный ответ - небольшой cleanup. Иногда лучше оставить код как есть, пока нет реальной причины его менять.

**Коротко:** code smells - полезные warning signs, но не автоматическая инструкция переписывать код.

## Refactoring

Refactoring - это изменение внутренней структуры кода без изменения внешнего поведения. Он улучшает readability, maintainability, testability или architecture, сохраняя то, что видят пользователи и callers.

Хороший refactoring обычно incremental. Он начинается с маленькой границы, сохраняет behavior стабильным и поддерживается тестами или понятным ручным checklist. Большие rewrites рискованнее, потому что меняют структуру и поведение одновременно.

Практические примеры refactoring:

- вынести mapper из `ViewModel`;
- разбить большую функцию на именованные шаги;
- вынести data access из UI layer;
- заменить duplicated logic общей функцией;
- ввести маленький interface, когда появился реальный второй implementation;
- сделать ownership состояния явным.

**Важно:** refactoring должен снижать сложность. Если он только перемещает код или добавляет слои без повышения безопасности изменений, он может быть не нужен.
