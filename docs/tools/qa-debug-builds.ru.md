# Сборки для тестирования и диагностики

Сборка для QA должна давать достаточно сведений, чтобы воспроизвести и классифицировать дефект без исходного кода и Android Studio. Показывай данные, которые помогают в реальном расследовании.

## Что должна показывать внутренняя сборка

Полезные сведения:

* окружение, адрес API, версию приложения, номер сборки и SHA коммита;
* состояние аккаунта и сессии без учётных данных и токенов;
* флаги функций и назначенные варианты экспериментов;
* сводку по локальной базе данных и кешу;
* метаданные недавних запросов, логи приложения и нормализованные ошибки;
* статус регистрации push-уведомлений без отображения токена;
* состояние фоновых задач и синхронизации;
* разрешения и значимые сведения об устройстве;
* идентификатор диагностики, связывающий данные приложения, сервера и теста.

Предпочитай сводки и управляемые действия неограниченному просмотру базы данных или файлов.

## Диагностический архив

```text
diagnostic-report/
├── app-metadata.json
├── device-metadata.json
├── feature-flags.json
├── recent-logs.txt
├── network-summary.json
├── local-state-summary.json
└── optional-screenshot-or-screen-recording
```

По возможности снимай согласованное состояние данных. Добавляй временные метки, версию схемы, версию приложения и ID отчёта. Ограничивай количество и возраст логов, а также размер архива. Формируй каждый файл из разрешённого списка полей, скрывай чувствительные значения до записи и проверяй готовый архив, включая необязательные снимки экрана и видео.

По умолчанию исключай пароли, токены авторизации, платёжные данные, неограниченные записи из продакшена и полные тела запросов и ответов. Экспорт должен запускаться явно; для переданного архива нужны правила хранения и доступа и понятный круг получателей. Снимок экрана может раскрыть больше, чем текстовый отчёт.

## Полезные действия для отладки

* сбросить онбординг или очистить локальный кеш;
* завершить текущую сессию через штатный выход из аккаунта;
* принудительно включить режим без сети;
* имитировать ошибку сервера, пустое состояние или частичный сбой;
* запустить синхронизацию или разрешённую фоновую задачу;
* скопировать ID диагностики;
* открыть внутренний экран;
* обновить флаги функций;
* воспроизвести заранее заданное состояние приложения.

По возможности используй те же сервисы приложения, что и обычные сценарии. Прямая правка хранилища может создать невозможное состояние. Явно обозначай имитацию в интерфейсе, обеспечь надёжный сброс и фиксируй активные настройки при регистрации дефекта.

## Архитектура и безопасность

Контракты диагностики размещай в интерфейсах приложения, а реализации — в наборах исходников внутренних вариантов сборки:

```text
QA / Debug UI
      ↓
Diagnostic queries and controlled commands
      ↓
Repositories, WorkManager, feature flags, logger, network summaries
```

Не включай привилегированные функции в релизный артефакт: проверяй содержимое собранного варианта, а не только флаг во время выполнения или скрытое меню. Внутренним сборкам также нужны контролируемая раздача, ограничения по окружениям и проверка доступа к чувствительным действиям. Протоколируй опасные операции и предусматривай отзыв доступа, если этого требует способ распространения. С данными продакшена во внутреннем APK обращайся так же аккуратно, как в публичном релизе.

Согласуй состав данных и действий с QA, мобильной и серверной командами, а также специалистами по безопасности и приватности. Показывай то, что сокращает расследование реального дефекта.
