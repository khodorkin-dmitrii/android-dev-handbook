# Binder IPC и AIDL

Binder - основной механизм межпроцессного взаимодействия (IPC) в Android. AIDL добавляет поверх Binder типизированный контракт и сгенерированный код. Код приложения чаще сталкивается с ними косвенно через framework managers, но понимание этой границы помогает правильно работать с bound services, потоками, ошибками и безопасностью.

## Зачем Android нужен IPC

Android-приложения обычно работают в отдельных Linux-процессах, часто под разными UID. Один процесс не может напрямую читать или изменять память другого. Такая изоляция ограничивает последствия ошибок и служит важной границей безопасности, но для передачи данных и вызова операций между процессами требуется IPC.

IPC используется, когда приложение обращается к компоненту в другом app process, а также когда публичный framework API взаимодействует с платформенной службой. Компонент приложения `Service` и платформенная или системная служба - разные понятия. Кроме того, `Service` не получает отдельный процесс или background thread автоматически: по умолчанию он работает в процессе приложения, а его callbacks выполняются в main thread этого процесса.

## Модель Binder

В Binder-взаимодействии участвуют несколько основных частей:

- клиентский процесс вызывает client-side proxy;
- proxy сериализует идентификатор метода и поддерживаемые значения в `Parcel`;
- Binder driver в ядре переносит транзакцию через границу процессов;
- Binder thread в серверном процессе принимает транзакцию;
- серверный Binder-объект или stub десериализует запрос и вызывает реализацию;
- для двустороннего вызова результат или исключение возвращается в reply `Parcel`.

```text
Client call
-> generated or handwritten proxy
-> request Parcel
-> Binder driver
-> server Binder thread
-> Stub / implementation
-> reply Parcel
-> client
```

Binder делает удаленную операцию похожей на вызов локального метода, но это лишь удобство API. Вызов по-прежнему требует сериализации, планирования и переключения контекста. Удаленный процесс может завершиться, транзакция может не выполниться, а сервер способен обрабатывать код конкурентно в потоках Binder pool. Если относиться к Binder-вызову как к обычному вызову в памяти, легко получить зависание UI и ненадежную обработку ошибок.

Многие Android framework API используют Binder внутри. Например, публичный manager может быть оболочкой приложения над удаленной платформенной службой. Обычному приложению следует работать через публичный SDK API, а не искать скрытые Binder services напрямую. Android использует Linux kernel; Binder поддерживает сервисную архитектуру платформы, но не превращает Android в microkernel OS.

## Что добавляет AIDL

Android Interface Definition Language (AIDL) описывает типизированный интерфейс, согласованный между процессами. Build tools генерируют Binder-обвязку, включая серверный `Stub` и клиентский `Proxy`. Сервер расширяет сгенерированный stub или делегирует ему работу, а клиент получает интерфейс из `IBinder`.

Аргументы, результаты и исключения должны допускать передачу через границу процессов. AIDL поддерживает примитивы, некоторые платформенные типы, другие AIDL-интерфейсы и объявленные parcelables. Для пользовательского типа требуется общее определение, которое обе стороны сериализуют одинаково. Например:

```aidl
// DeviceStatus.aidl
package com.example.status;

parcelable DeviceStatus;
```

```aidl
// IDeviceStatusService.aidl
package com.example.status;

interface IDeviceStatusService {
    DeviceStatus getStatus();
}
```

Здесь `DeviceStatus` должен быть поддерживаемым AIDL типом `Parcelable` в том же package, а клиент и сервер должны использовать его совместимое определение. AIDL не заменяет Binder и не является другим транспортом. Он генерирует типизированный Binder-интерфейс и берет на себя значительную часть шаблонного кода сериализации и диспетчеризации.

## Связь с bound service

Приложение может предоставить Binder endpoint через [bound `Service`](components.md#bound-service). Сервер возвращает `IBinder` из `Service.onBind()`. После `bindService()` клиент асинхронно получает binder в `ServiceConnection.onServiceConnected()` и использует его только в течение жизни соединения.

Следует выбирать самый простой механизм, который соответствует границе процессов и требованиям к конкурентности:

| Вариант | Когда подходит |
| --- | --- |
| Custom `Binder` | Клиент и service работают в одном процессе |
| `Messenger` | Межпроцессные message-based запросы с последовательной обработкой |
| AIDL | Типизированный межпроцессный контракт, возможно с несколькими конкурентными клиентами |

Для распространенного варианта в одном процессе custom `Binder` проще. `Messenger` передает сообщения через `Handler`, поэтому удобен, когда запросы должны обрабатываться последовательно. Прямой AIDL оправдан, если действительно нужен стабильный типизированный API между процессами и реализация готова к конкурентным вызовам. Для обычного application service это не вариант по умолчанию.

## Потоки, время жизни и ошибки

Удаленные AIDL-методы по умолчанию синхронные: клиент ждет ответа сервера. Потенциально медленный удаленный вызов нельзя выполнять в main thread. Даже простой на вид метод может заблокироваться, если сервер занят, выполняет I/O или ожидает свободный Binder thread. Payload также должен быть небольшим: Binder transactions используют ограниченные буферы и не предназначены для передачи крупных файлов, bitmap или графов объектов. Для больших данных лучше передать file descriptor, URI или идентификатор.

Входящие удаленные вызовы обычно выполняются в потоках Binder pool серверного процесса. Реализация service должна защищать изменяемое состояние и явно определять модель конкурентности. Вызов внутри одного процесса может быть оптимизирован до прямого и выполниться в потоке клиента, поэтому локальное и удаленное размещение способны давать разное threading behavior. Не следует рассчитывать, что Binder сам перенесет работу в определенный поток приложения.

Модификатор AIDL `oneway` делает удаленный вызов асинхронным с точки зрения клиента, но такой метод не может вернуть результат. Он не отменяет необходимость продумать нагрузку, порядок и ошибки, поэтому подходит только для настоящей fire-and-forget семантики.

Удаленный процесс может завершиться в любой момент. Вызов способен выбросить `RemoteException`, а клиент bound service должен корректно обработать `ServiceConnection.onServiceDisconnected()` и другие подходящие callbacks потери соединения. `IBinder.DeathRecipient` - более низкоуровневый механизм наблюдения за смертью Binder endpoint для сложных интеграций. При любом варианте IPC вызов `bindService()` нужно сопоставить с `unbindService()` согласно lifecycle владельца соединения.

## Граница безопасности

Экспортируемый bound service создает IPC entry point, к которому может попытаться обратиться другое приложение. Для подключения к известному service лучше использовать explicit `Intent`, а приватный service объявлять с `android:exported="false"`. Если соединение с другими приложениями необходимо, чувствительные операции нужно защищать подходящими permissions и проверять право каждого caller на запрошенное действие.

Binder предоставляет сведения о caller, включая UID и PID, через `Binder.getCallingUid()` и `Binder.getCallingPid()`. Эти данные нужны для решения об авторизации, но сами по себе не являются авторизацией. При необходимости следует учитывать shared UID, проверять package или подпись через поддерживаемые API и не доверять переданным клиентом полям с его идентичностью. Binder безопасно переносит запрос через границу процессов, но не делает экспортируемый контракт безопасным автоматически.

## AIDL приложений и платформенный AIDL

Разработчик приложения может использовать AIDL напрямую между собственными процессами или взаимодействующими приложениями. Это app-level модель из документации Android Developers. Отдельно Android framework services используют множество внутренних AIDL-контрактов за публичными managers и SDK API. Доступ к скрытому `ServiceManager` и внутренним AOSP interfaces - детали реализации, а не поддерживаемый публичный API для обычных приложений.

Stable AIDL добавляет контроль совместимости и версионирование для платформенных компонентов, которые могут обновляться независимо, включая некоторые границы APEX и HAL. Он решает задачу платформенной интеграции и вводит более строгие правила интерфейса. Обычному application-level AIDL service, как правило, не нужен build workflow Stable AIDL.
