# Общий и платформенный код

KMP допускает разные границы переиспользования. Выбирайте ту, которая убирает полезное дублирование, не заталкивая платформенное поведение в общий код.

| Стратегия | Общее | Платформенное | Типичный сценарий |
| --- | --- | --- | --- |
| Общая основа | Модели, форматирование, алгоритмы | Большая часть приложения | Библиотеки или первое внедрение KMP |
| Общий слой данных | API, сериализация, логика хранения, репозитории | Представление и UI | Постепенное внедрение |
| Данные и домен | Данные, репозитории, бизнес-правила, сценарии | ViewModel и UI | Отдельные команды нативного UI |
| Общее представление | Данные, домен, состояние UI и его владельцы | Нативный UI и навигация | Единое поведение при нативном UI |
| Общий UI | Общая логика и Compose UI | Точки входа и платформенные интеграции | Похожие продукты на разных платформах |
| Гибрид | Отдельные функции, слои или UI-компоненты | Остальное | Разные требования платформ |

## Граница по ответственности

### Источники данных и репозитории

HTTP-поведение, сериализацию, DTO, SQL-запросы, правила кеширования, пагинацию, повторы и синхронизацию часто можно разделить между платформами. Настройка базы данных, пути файловой системы, защищённое хранение, наблюдение за сетью, фоновая работа и push-уведомления могут требовать платформенных реализаций. Перед переносом API в общий код проверьте поддержку каждого target библиотекой.

Общие репозитории полезны, когда они координируют локальные и удалённые данные, задают источник истины *внутри каждого приложения* и применяют одинаковые правила офлайн-работы и актуальности данных. Общий код репозитория не означает общую базу данных или кеш для установок Android и iOS.

### Домен и представление

Доменные модели, валидация, фильтрация, сортировка и бизнес-правила часто переносимы. Добавляйте сценарий использования, когда он выражает значимую операцию или координацию, а не только оборачивает метод репозитория.

В представлении можно переиспользовать `UiState`, действия, владельцев состояния или ViewModel, а также обработку загрузки, ошибок, офлайн-режима и повторов через `StateFlow`. Отдельно решите, кто на каждой платформе отвечает за жизненный цикл, восстановление состояния, навигацию и разрешения. Учитывайте взаимодействие Kotlin и Swift, если нативный iOS UI получает общее состояние.

UI может оставаться на Jetpack Compose и SwiftUI, использовать Compose Multiplatform для отдельных экранов или разделять Compose UI между Android и Desktop, сохраняя нативный iOS UI. Подробнее — в статье [«Архитектура и стратегии UI»](architecture-ui.md).

## Интерфейсы и `expect`/`actual`

Для заменяемого поведения, например открытия ссылок, хранения данных, наблюдения за сетью и аналитики, используйте интерфейс с внедряемыми реализациями:

```kotlin
// commonMain
interface ExternalLinks {
    fun open(url: String)
}

class HelpPresenter(private val links: ExternalLinks) {
    fun openHelp() = links.open("https://example.com/help")
}
```

`expect`/`actual` подходит для небольшого платформенного моста с одинаковым API для каждого target:

```kotlin
// commonMain
expect fun platformName(): String

// androidMain
actual fun platformName(): String = "Android"

// iosMain (охватывает объявленные targets устройства и симулятора iOS)
actual fun platformName(): String = "iOS"
```

Компилятор требует подходящее объявление `actual` для каждого target; промежуточный source set, например `iosMain`, может покрыть несколько targets. Классы `expect`/`actual` всё ещё имеют статус Beta, поэтому функция или свойство часто служит более узким мостом. Интерфейсы проще подменять в тестах и реализовывать несколькими способами на одной платформе.

См. [Структура проекта и source sets](project-structure.md) и [Внедрение KMP и компромиссы](adoption-tradeoffs.md).
