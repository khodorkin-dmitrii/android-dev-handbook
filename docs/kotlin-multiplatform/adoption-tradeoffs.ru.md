# Внедрение KMP и компромиссы

KMP - архитектурная инвестиция, а не обязательный выбор по умолчанию. Польза появляется, когда платформы разделяют существенное поведение, но сохраняют необходимые нативные интеграции.

## Признаки подходящего проекта

KMP стоит рассмотреть, когда:

- бизнес-поведение должно оставаться согласованным между платформами;
- есть существенная data-, domain-, synchronization- или offline-first логика;
- команды могут совместно владеть Kotlin-кодом и native integration;
- требования платформенных продуктов совместимы;
- можно организовать shared ownership, code review, tests и CI;
- стабильную ответственность можно извлечь постепенно.

Подходящая [граница переиспользования](shared-platform-code.md) может проходить после небольшого core, data и domain, presentation, UI или различаться по features.

## Издержки и риски

Внедрение усложняет build configuration и CI, расширяет test matrix и требует проверки совместимости библиотек с targets. Kotlin/Swift interoperability усложняет exported API, coroutines, errors, generics и debugging между языками. Platform API, lifecycle и native toolchains остаются необходимыми. Для Apple builds и финальной проверки Apple-платформ нужны macOS и Xcode.

Организационная стоимость не менее важна. Нужно определить владельцев shared modules, platform adapters, reviews, releases и upgrade coordination. Общий модуль без общей ответственности может стать bottleneck.

[Source-set design](project-structure.md) управляет доступностью зависимостей, но не устраняет стоимость интеграции. Общие [ViewModel или UI](architecture-ui.md) также не отменяют platform lifecycle, navigation, accessibility и system behavior.

## Постепенное внедрение

1. Найдите стабильную и тестируемую ответственность.
2. Извлеките небольшой shared module.
3. Создайте явные platform adapters.
4. Добавьте shared tests и target-aware CI.
5. Измерьте стоимость сопровождения и integration friction.
6. Расширяйте границу только после подтверждения пользы.

Полная перепись редко является безопасным вариантом по умолчанию. Networking models, валидация, форматирование или изолированный repository обычно подходят для эксперимента лучше, чем миграция всего приложения.

## Когда KMP может не окупиться

KMP может быть неоправдан, если переиспользовать почти нечего, платформы намеренно реализуют разные продукты или приложение слишком маленькое либо краткосрочное. Риск также высок, если команда не может владеть Kotlin и native integration, критическая зависимость не поддерживает нужные targets или организационные границы мешают shared ownership.

## Чек-лист решения

- Какое стабильное поведение станет общим?
- Какие targets и библиотеки обязательны?
- Где пройдёт platform boundary?
- Кто владеет shared code и каждым adapter?
- Как каждый target будет собираться, тестироваться и выпускаться?
- Какая метрика покажет снижение дублирования, расхождений или времени поставки?
- Есть ли постепенный путь назад, если эксперимент не окупится?

Выбирайте KMP, когда ожидаемая продуктовая и эксплуатационная польза превышает технические и организационные издержки, а не ради максимального процента общего кода.
